## 0. 一句话结论

vBookmarks 拥有**品类里最完整的书签树交互底子**（懒加载树、全键盘导航、拖拽、分隔符、omnibox、42 语言），但当前主分支存在三处致命回归、存储体系分裂脑、视觉停留在 2011 年。演进方向：**不引入框架**，用 MV3 原生能力（ES modules + side panel + commands + CSS tokens）把它重塑为 **"Raycast 的速度感 × Arc 的侧栏组织感"** 的键盘优先书签中枢——快、暗、安静，且仍然是零依赖的本地优先扩展。

## 1. 现状诊断摘要

### 1.1 值得保留的资产（不要重写掉的）

- **功能完整度**：树的全部管理操作 + type-ahead 定位 + F2/Delete + 自绘右键菜单 + 跨文件夹拖拽排序——这套交互密度在今天的扩展商店里依然稀缺。
- **chrome.bookmarks 直读、零云端**：无数据锁定、无账号、无隐私顾虑。这是相对 Raindrop/Karakeep 等云服务的根本差异化，必须守住。
- **零依赖、零构建、安装体积极小**：调试成本极低，`font: menu` 的原生质感本身就是早期的好品味。
- 42 语言 i18n 体系与 `_m()` 约定，是多数同类扩展没有的积累。

### 1.2 致命问题（P0，当前版本实际损坏）

证据与细节见架构篇，此处只列结论：

1. **`storage.js` 解析期崩溃**：整个文件内容被完整重复粘贴了一遍，两次 `class StorageManager` 声明导致 SyntaxError，`node --check` 实测复现。→ popup.js / options.js 初始化连带全崩。
2. **omnibox 回车失效**：`background.js:93` 的 `const firstResult` 遮蔽外层 `let`，`onInputEntered` 里 `!firstResult` 恒真，回车永不打开书签。
3. **设置页分裂脑**：options.js 把开关写入 `chrome.storage.local`，neat.js 却从 `localStorage` 读同名 key——**设置页对弹窗大部分无效**；且没有老数据迁移代码。

另有一个发版级隐患：`scripts/package.py` 漏打 `storage.js`/`sync-manager.js`/`sync-styles.css`，照此打包即事故。

### 1.3 系统性技术债（按影响排序）

- **存储层**：localStorage（97 处）/ chrome.storage.local / chrome.storage.sync 三套体系混用，无迁移路径；滚动、开合文件夹、拖拽 resize 等高频动作同步直写 localStorage。
- **巨石架构**：neat.js 3229 行单 IIFE；neatools.js 大面积 monkey-patch 内置原型；三者（含 background.js、sync-manager.js）均不可 import，测试只能测"抄写本"，等于没有回归保护。
- **SyncManager 错位**：生在 popup、死在 popup，"60 秒自动刷新"只在弹窗开着时存在；undo 栈随页面消亡；状态判定回退逻辑语义错误。
- **manifest 冗余**：`identity` 权限从未使用；`<all_urls>` 无正当用途（bookmarklet 路径因缺 `scripting` 权限和缺失的 content-script.js 必然抛错）；MV2 遗物（update_url、background.html、checkupdate.json）；CSP 与自定义 CSS 功能直接冲突。

### 1.4 体验的时代差

- 无任何暗色支持（sync-styles.css 里的暗色规则作用对象在 DOM 中不存在）；配色、尺寸全部硬编码；无 design tokens。
- 无空状态、无加载态：搜索无结果是沉默的空白，树加载是白屏。
- 图标为 16px 位图（folder.png 等），无 SVG、无高分屏体系。
- 交互硬件层多处废弃 API：`<menu type="context">`、2009 版 flexbox、CSS `zoom`、`document.execCommand`、`navigator.platform` sniffing。
- 可访问性近乎缺席：菜单无 role、对话框无焦点圈禁、选中态去除 outline。
- 搜索是 Chrome 原生子串匹配 + 自写排序——2026 年的用户预期是模糊匹配。

## 2. 目标体验："新时代 taste" 的定义

品味不是风格叠加，而是一组自洽的取舍。vBookmarks 的目标体验定义为三条原则：

### 2.1 速度感（学 Raycast）

- **time-to-first-result 是第一指标**：弹窗/侧栏打开即聚焦搜索框，输入即出结果，首条结果永远可被 Enter 直接打开。
- **键盘全可达**：今天已有的键盘导航是底子，要补齐的是"唤醒层"——`chrome.commands` 绑定全局快捷键唤起侧栏/搜索，面板内 ⌘K 风格命令面板统一"搜书签 + 执行动作"（对标 [Omni](https://github.com/alyssaxuu/omni) 的斜杠命令：`/folders`、`/dupes`、`/dead`）。
- 一切阻碍速度的东西让路：搜索输入防抖、结果虚拟化、首屏只渲染可视区。

### 2.2 秩序感（学 Arc / Raindrop）

- **主界面从 320px popup 升级为 side panel（可选开启，默认关闭）**：现有数万用户的肌肉记忆不可破坏——popup 永远保持默认且功能完整；side panel 作为设置项开启后，action 点击切换为开侧栏（`openPanelOnActionClick` 运行时切换）。面板内双栏：左文件夹树，右当前文件夹书签列表——树负责"组织"，列表负责"浏览与批量操作"。
- **保存即整理**：新增书签的对话框升级为一站式保存流（标题 / 文件夹选择器 / 备注），消灭"先存后整理"的二次劳动。
- 文件夹 ⇄ tab group 的映射：一键"全部打开为标签组"，让书签秩序延伸到浏览器秩序。

### 2.3 安静感（calm UI）

- **design tokens 化**：全部颜色收敛为语义变量（`--bg` / `--fg` / `--muted` / `--accent` / `--danger` / `--border`），亮暗双主题 + `prefers-color-scheme` 自动跟随 + 设置页手动覆盖。暗色不是反色，是重新设计：深灰底（非纯黑）、降对比的层级、accent 色提亮。
- **密度与字体**：系统字体栈 13px、行高 1.45、行高 28–32px 的紧凑列表；缩进从 14px 收敛到 12px；twisty 改为 chevron。
- **克制的动效**：150–250ms ease-out 单一节奏；twisty 旋转、hover 微变色、命令面板 120ms 的 scale(0.98→1) 弹出；不做玻璃拟态等重装饰——书签工具的美感来自"快而准"，不是通透感。
- **图标体系换代**：favicon 继续走 `/_favicon/`（隐私友好，已在用）；folder.png / document-code.png 等位图换成内联线性 SVG（1.5px 描边、16px 网格、currentColor），随主题变色。
- **有文案的空态**：空文件夹、搜索无结果、首次使用，各有一句人话 + 一个引导动作（如"按 Ctrl+D 收藏当前页"）。

## 3. 技术路线决策（关键取舍）

**决策：保持 vanilla，不引入框架和打包器；用 MV3 原生 ES modules 拆分巨石。**

理由：

1. MV3 扩展页面原生支持 `<script type="module">`，service worker 已是 `"type": "module"`——模块拆分不需要任何工具链。
2. 本项目的核心价值是 chrome.bookmarks API 之上的交互层，没有复杂状态同步问题，React/Vue 解决不了这里的真问题（DOM 渲染性能靠虚拟滚动和增量渲染解决，不靠虚拟 DOM）。
3. 零构建是这个仓库的身份与优势：引入 WXT/React 意味着 node_modules、构建调试、source map 调试真实代码——维护成本对一个单人维护项目不成比例。
4. CSS 用原生 custom properties + 现代选择器（`:has()`、容器查询）足够实现 tokens 体系。

**拆分蓝图**（neat.js 3229 行 → `src/` 下 ES modules，每模块 < 400 行）：

| 模块 | 来源（neat.js 行号） | 职责 |
|---|---|---|
| `store.js` | storage.js + 89 处 localStorage | 唯一存储入口：get/set/默认值/迁移/变更订阅 |
| `tree-view.js` | 384-855 | 树渲染、懒加载、展开状态记忆 |
| `search.js` | 954-1164 + background ranking | 模糊匹配 + 排序权重（前后台共用一份纯函数，可被 vitest 真测） |
| `actions.js` | 1454-1757 | 打开/编辑/删除/批量等动作表 |
| `context-menu.js` | 1866-2182 | 右键菜单（换标准元素 + role） |
| `keyboard.js` | 2184-2571, 2969-3059 | 键盘导航与快捷键 |
| `dnd.js` | 2573-2867 | 拖拽排序 |
| `dialogs.js` | 1206-1326 | 对话框（加焦点圈禁） |
| `separators.js` | 68-144 | 分隔符 |
| `sync-ui.js` | 3113-3229 + sync-manager.js | 同步指示 |

neatools.js 整体退役（替代对照表见 UI 篇 §5）；原型污染全部改纯函数。纯逻辑（search ranking、separator 判定、URL 归一化、sync 状态机）放进无副作用模块，vitest 直接 import 真源码——测试从"抄写本"变回保护网。

**例外条款**：若未来决定做卡片网格视图 + AI 打标 + 多视图切换的重 UI 版本，再评估 WXT + Svelte；那是另一个产品，不是这次演进。

### Phase 4 — 前沿选项（独立评估，不承诺排期）

- **AI 自动打标/建议文件夹**：优先 Chrome 内置 Prompt API（Gemini Nano，本地、隐私一致），或用户自带 key；默认关闭。
- **封面缩略图/卡片视图**：保存时 `captureVisibleTab` 截图存 storage.local；树视图与卡片视图切换。
- **稍后读集成**：`chrome.readingList` 双向入口。
- 共同约束：不引入云端账号体系；任何新权限单独评估安装警告成本。

## 5. 风险与约束

- **权限警告变化**：删 `<all_urls>`/`identity` 是减负；若 Phase 3 死链扫描需要 `<all_urls>` 抓页面，需用 optional_permissions 按需申请，避免全量用户被新警告打扰。
- **老用户迁移**：Phase 1 的存储迁移是唯一高风险点——必须幂等、可重入、保留 localStorage 原数据至少一个大版本；42 语言的存量用户意味着任何破坏都会放大。
- **i18n 流程**：Phase 2 起新增大量 UI 文案，坚持"en 先行 + sync_locales.py 传播 + check_translations.py 校验"；新交互（命令面板）的文案要短，mk/pt_BR/pt_PT 已有欠账。
- **Chrome 版本基线**：sidePanel 要 114+，`syncing`/`folderType` 要 138+，minimum_chrome_version 88 名存实亡——Phase 1 统一做特性检测 + 优雅降级，再抬基线。
- **范围纪律**：本方案的边界是"书签管理器"，不做 tab 管理器、不做 read-later 全家桶、不做云同步服务——品类调研里的方向只取与 chrome.bookmarks 直读模型自洽的部分。

## 7. 增补决策（2026-07-17，维护者评审后）

### 7.1 侧栏策略：popup 永远是默认，panel 是可关闭的可选增强

现有数万用户的习惯是第一约束。最终决策：

- **popup 保持默认且功能完整**，不做任何裁剪；`manifest.action.default_popup` 始终保留。
- side panel 以**设置项**（默认关闭）提供：开启后调用 `chrome.sidePanel.setPanelBehavior({openPanelOnActionClick:true})`，action 点击变为开侧栏；关闭即恢复原行为。另提供 `chrome.commands` 快捷键随时开侧栏（不依赖该开关）。
- 面板复用 popup 同一套代码（`side_panel.default_path` 指向 `popup.html?panel=1`），以 body class + CSS 做宽版/双栏适配，不复制实现。
- 未来的重 UI（卡片网格、AI 打标等）若做，只进 panel，不进 popup。
- 该决策同时回应 issue #28（全览展开页）：面板提供常驻大空间，多列卡片视图列为 Phase 4 候选。

### 7.3 框架决策：零依赖 vanilla + 自研微型 DOM 助手库（neatools 的精神继承）

评估过程：

- **MV3 硬约束**：扩展页 CSP 禁止 `'unsafe-eval'`（MV3 不允许覆盖），Alpine.js 标准版、petite-vue 等运行时编译模板的框架（内部 `new Function`）**直接出局**；Alpine 官方 CSP build 可行但要求组件预定义、交互表达力下降，且引入第三方依赖。
- **Preact + htm（无构建）** CSP 安全、体积小，但本代码库是高密度命令式 UI（自绘拖拽、右键菜单、虚拟滚动、大量直接 DOM 操作），VDOM 化等于重写，风险/收益不成比例。
- **结论**：不引入框架。将 neatools 的"极致轻量类 jQuery"精神现代化为 `src/dom.js`（ES module，约 150 行）：`h()` hyperscript 建节点、`$`/`$$`、`on()` 委托、`escapeHtml` 等纯函数，零依赖、CSP 免疫、无原型污染。事件委托 + 直接 DOM 恰恰是本场景最快的方案，"轻量、快速"底线不受任何影响。
- neatools.js 按 UI 篇 §5 对照表退役，monkey-patch 全部纯函数化。
