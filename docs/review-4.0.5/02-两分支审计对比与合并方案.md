# vBookmarks 4.0.5：k3(master) 与 glm53 两分支审计对比与合并方案

> 分析日期：2026-08-14
> 分析对象：
> - **master（k3 方向）**：`f0a975b` 之后 4 个审计批次（A/B/C/D）+ 文档 E1，HEAD = `ffc68fa`
> - **v4.0.5-qoder-glm5.3-audit（glm53 方向）**：`f0a975b` 之后 P1–P5 批次，HEAD = `fdef43f`
> 共同基点：`f0a975b`（4.0.5 版本号提升），两分支**完全分叉、互不包含**（`git merge-base` = `f0a975b`）。
> 方法：通读两份审计报告（`docs/review-4.0.5/01-audit-and-plan-k3.md` vs `docs/review-4.0.5/00-audit-and-plan-glm53.md`）、两份 4.1.0 设计文档（`v4.1.0task-1-k3.md` vs `v4.1.0task-1-glm53.md`）+ 四路并行逐文件代码 diff（src / tests / css / 工程配置）。
> 结论：**4.0.5 应以 master 为主体、系统性吸纳 glm53 的独有修复；两分支几乎无冗余重复，绝大多数改动互补，少数「相反决策」需要逐项裁决。4.1.0 设计以 glm53 的三平面模型 + 4px 网格契约为地基、master 的 Calm Instrument 语言与静态 JSON 公告为顶冠，融合定稿。**

## 0. 结论速览（TL;DR）

### 0.1 两分支的「性格」差异

| 维度 | master (k3) | glm53 |
|---|---|---|
| 方法论 | 按文件/模块切 4 批次（A 面板模糊 / B 焦点 / C 视觉 favicon / D 死链去重转义） | 按问题域分级（A1–A6 确定缺陷 / B1–B9 抛光 / C1–C6 文档 / D1–D10 接受）+ P1–P5 批次 |
| 强项 | **机制级修复**：focusSpot/rowFocusTarget 契约、menuOpen 可见性、viewState 门控、徽标树 join 一致性 | **点状补漏**：观察器 bug、alias 注入、树焦点律、matcher 自转义、focus-visible、幽灵槽、死规则 |
| 弱项 | 有真实 bug 未发现（favicon 观察器永不安装、alias 注入面、树 park/unpark） | 未触碰一批机制（undo toast Tab 环、viewState 门控、context-menu 禁用态、RTL、storage 直推） |

### 0.2 核心结论

1. **两分支的审计发现几乎不重叠**。真正「两边都发现」的只有三处：favicon 主题动态链（且修复点不同）、删除红语义铺全（都做）、i18n/文档同步（都做）。其余 30+ 项均为单边独有——**这不是重复劳动，是两次互补的审计**。
2. **必须保留 master 的**：favicon 反色策略重写（13 真实图标矩阵实证）、escape.js 补 `&`（全量调用方审计）、rowFocusTarget 契约、viewState/rememberState 门控、undo toast Tab 环、view-dupes 删除链、view-dead 徽标树 join、context-menu 禁用态、RTL、storage.onChanged、i18n 388 键。
3. **必须从 glm53 吸收的**：favicon 观察器守卫 bug 修复（基点 f0a975b 即存在、master 沿用未发现）、palette slash/aliases 注入双层防御、树视图 generateTree park/unpark + focusID 守卫、历史区 focusSpot（`hist:` 键）、工具栏恢复 cls+idx（比 master 裸索引稳）、matcher 自转义 + 子序列高亮、omnibox/popup 排序契约测试、`:focus-visible`、死链选择态幽灵槽、package.py 种子清单、`doc.defaultView.matchMedia`（可注入，比全局更可测）。
4. **真正需要人工裁决的相反决策**（详见 §5.2）：escape.js `&`、dead-start `:focus` vs `:focus-visible`、danger hover tint 保留/删除、list-focus 两套 API、matcher/background 转义配对、favicon 策略、view-dead 徽标/冷启动 preload。
5. **合并后 4.0.5 测试规模预计 66+ 套件 / 2060+ 例**，需重新走全量 vitest + lint + i18n 三门禁。

### 0.3 4.1.0 设计融合方向

- **地基（glm53 胜）**：三平面深度模型（`--vbm-canvas`，解决 k3 方案 light 下「卡片浮白底不可见」的必然翻车）、4px 基准网格契约、`/theme` 列表模式（替代 k3 的 `/next-theme` 盲循环）、options.css 单源化、状态 token 表。
- **顶冠（k3 胜）**：Calm Instrument 语言总纲与主题签名（ink 磷光 / paper 朱砂）、token 级 classic（K2，与 glm53 R3 不谋而合）、**静态 JSON 公告层**（碾压 glm53 的 Upstash：零密钥零依赖零隐私风险）、完整应用壳独立页（K9）、`/copy markdown`、`/open-all` 先行版。
- **明确否决（两者合取）**：`chrome.theme` 跟随、侧边栏双栏、macro 实施、auto→ink 映射、计算器（k3 K5 否决；glm53 R5 的递归下降实现可留作 4.2 参考）、`/toggle`（glm53 R6 心智模型论证更充分）、`visited:N` token（glm53 R7 的 visitStats 语义论证成立）。

### 3.3 同一文件多方向改动 → 需人工整合

**view-dead.js**：master 动了徽标/onCreated/过滤集/确认文案（机制），glm53 动了工具栏恢复（cls+idx）与死链选择态视觉。两者区域不重叠，**可叠加**，但工具栏 API 以 glm53 为准（见 §5.2.4）。

**list-focus.js（合并核心冲突）**：两套不兼容 API——

| | master | glm53 |
|---|---|---|
| 行契约 | 导出 `rowFocusTarget(li)`；`unparkRowFocus(list, parked, emptyFocus)` 3 参 | 无 rowFocusTarget（内联）；`unparkRowFocus(list, parked)` 2 参 |
| 工具栏 | `TOOLBAR_SEL`/`TOOLBAR_SEL_RISK` + 裸索引 `toolbarFocusIndex`/`restoreToolbarFocus(root, idx, sel)` | `TOOLBAR_CONTROLS_SEL` + `parkToolbarFocus(root)→{cls,idx}`/`restoreToolbarFocus(root, parked)` |

**merge 时必须以一方 API 为基底。裁决见 §5.2.4：保留 master 的 `rowFocusTarget` 行契约（glm53 没有，其 view-manager 恢复路径保留着 `li.firstElementChild` 旧 bug），采用 glm53 的 cls+idx 工具栏（master 的裸索引在按钮增删时漂移）。**

## 5. 综合评判：4.0.5 合并方案（逐项裁决）

### 5.1 合并策略总纲

**以 master 为主体分支，cherry-pick / 手合 glm53 的独有修复；关键「相反决策」按 §5.2 裁决后统一代码形态。** 理由：
1. master 的机制级修复（focusSpot/rowFocusTarget/menuOpen/viewState/徽标一致性）是**结构性**的，glm53 没有；而 glm53 的修复大多可叠加在 master 之上。
2. master 有 `vitest.config.js`，测试计数可信。
3. master 的 favicon 反色重写有 **tmp/favicon-lab 实验实证**（13 真实图标 × 4 主题矩阵），这是用户反馈驱动的真实价值；glm53 保留均值策略只是因为没看到反馈。

### 5.2 需要人工裁决的相反决策（逐一）

#### 5.2.1 favicon 判定算法 → **master（极端色占比）**
- glm53 保留均值策略是「BASE 现状」，其 A2/A3 修的是动态链；而 master 的批次C 依据用户指出的失效案例（澎湃黑标、GitHub 黑标、Yanu 青蓝、雅书白标）做了实验重写。均值对「主体色占比」不敏感的根本缺陷已由矩阵证实。
- **但**：观察器守卫 bug（`typeof doc.body.observe === 'function'` 恒 false）必须用 glm53 的 A2 修复补上——该 bug 在共同基点 f0a975b 即逐字存在，master 沿用未发现，glm53 是真正修复者；matchMedia 用 glm53 的 `doc.defaultView.matchMedia` 写法（可注入、测试友好）。
- **结论**：`contrastStats`/`needsContrast` 用 master（极端占比 + 保色相滤镜），`initFaviconFallback` 的动态链（观察器守卫 + matchMedia + 返回 `themeMedia`）用 glm53，再叠加 master 的 `storage.onChanged` 直推。三部分来源不同，但目标一致，手合时逐段取优。

#### 5.2.2 escape.js `&` 转义 → **master（补 `&`）**
- glm53 的 D1「不转义以保幂等」写于审计早期，其顾虑（`highlightTitlePositions` 双喂会毁 `&lt;`）已被 master 批次 D 逐调用方核实否定：所有 9 个调用方 + 高亮函数均喂原始数据，`43442a6` 的转义下沉已消除双喂路径。master 新增 `&` 断言，且**改后全量测试绿**。
- glm53 侧没有做这个核实，其「不改」是保守而非正确。**采纳 master 的完备化**。

#### 5.2.3 dead-start `:focus` → **glm53（`:focus-visible`）**
- 鼠标点击死链「开始扫描」行不该显焦点环。glm53 B6 明确正确，master 保留 `:focus` 是遗漏。**采纳 glm53**，且同步其 `list-view-parity.test.js` 断言「不含 `:focus`」。

#### 5.2.4 list-focus.js 两套 API → **行契约取 master，工具栏取 glm53**
- **行焦点**：master 的 `rowFocusTarget` 是导出契约（view-manager 两处共用），修了 dupes keeper-radio 在 DOM 序前导致 `li.focus()` no-op 的真实 bug；glm53 保留 BASE 的 `li.firstElementChild` 启发式（对 button 打头行回退到 li，正是 master 修的 bug）。**行契约用 master**。
- **工具栏恢复**：master 用裸位置索引（`toolbarFocusIndex`），glm53 用 `{cls, idx}`（focusSpot 同款键），按钮增删不漂移——glm53 更稳（glm53 审计 B2 就是点名 master 这个裸索引问题，只是当时两边独立发展）。**工具栏用 glm53 的 `parkToolbarFocus`/`restoreToolbarFocus`**。
- **emptyFocus 参数**：master 的 `unparkRowFocus(list, parked, emptyFocus)` 让 search 历史区空列表时焦点回搜索框，是有用回退，保留。
- **合并形态**：`list-focus.js` = master 的 `rowFocusTarget` + `emptyFocus` 版 `unparkRowFocus` + glm53 的 `TOOLBAR_CONTROLS_SEL`/`parkToolbarFocus`/`restoreToolbarFocus`。配套改动 view-manager（import 保留 rowFocusTarget）、view-dead/dupes/stats（工具栏调用换 cls+idx）、search.js（委托 master 版）。

#### 5.2.5 view-dead 徽标 / 冷启动 preload → **master**
- master 把徽标改为树 join 行集派生（`allResultRows().length`）并删冷启动 preload，消除「重开 popup 复活旧计数」通路；glm53 保留裸缓存计数 + preload。master 的「徽标=列表行数」一致性论证更正确。**采纳 master**，测试按 master 新契约。

#### 5.2.6 matcher/background 转义配对 → **成套取 glm53**
- glm53 的 matcher 自持转义（`escapeRegExp`）+ 子序列高亮，并撤掉 background.js 调用方预转义。若保留 master 的 background.js 预转义 + glm53 matcher 自转义 = **双重转义**（`c++`→`c\+\+`→`c\\+\\+`）；反之 matcher 不转义 + 调用方也不转义 = SyntaxError。
- **裁决**：采纳 glm53 成套（matcher 自转义 + background.js 直传 `value`）。同时保留 master 的 fuzzy İ remap（这是另一个层面的位置修复，互补）。排序契约测试（G8）一并收。

#### 5.2.7 WORD_SEPARATORS 删 `;` → **采纳 master，但记录行为变化**
- master 把 `WORD_SEPARATORS` 中重复的 `;` 删去，改变含 `;` 标题的 tier-2 word-start 边界判定。这是行为变化，两分支对含 `;` 文本排序会分叉。**采纳 master**（重复字符删去是正确清理），但合并后需确认无存量用户依赖。

#### 5.2.8 danger hover tint → **采纳 master（保留 tint）**
- glm53 的 P4 删除了 `.dead-delete-all:hover` 等 danger-tint，视作死规则清理；但 master 批次 C 的方向是「danger 淡色 hover 统一」——这是视觉语义一致，不是冗余。**保留 master 的 tint**；只采纳 glm53 对**真正的**死规则清理（`.dead-proxy-chip.template`、`.stats-add-btn:hover` 重复声明、`#dead-list .row-btn.dead-mark-btn` 空体）与 D5 注释。

2. **list-focus 合流是最大风险点**：两套 API 不能靠 git 三方合并自动解决，必须手写合流文件并跑全套 view/键盘测试。
3. **favicon 三来源合流**：算法（master）/动态链（glm53）/直推（master）三处来源不同，需逐段核对，favicon 89 例测试是门禁。
4. **matcher 配对**：background.js 与 search-core.js 必须同批次改，否则双重转义或 SyntaxError。建议合流时在一个提交内完成。
5. **`.qoder/` 环境**：若在含 `.qoder` worktree 的环境跑 glm53 侧测试会失真——合流后必须保留 master 的 `vitest.config.js`。
6. **4.1.0 公告层**：静态 JSON 方案下，`docs/announce.json` 的 schema 校验（`tests/announce.test.js`）与发布 checklist 需同步进 AGENTS.md。
