## 2. 前史:问题类的诞生与掩蔽(审计要点)

1. **≤4.0.8 无此问题类**:innerHTML 换树后全树布局同步完成,一次性 `scrollTop = saved` 天然落地;裸 `focus()`(无 preventScroll)把视口拽向高亮行,兼任①近似位置恢复②**强制目标区布局(天然破死锁)**③回写自洽。
2. **v4.1.0 亲手制造问题类**(2026-08-27 性能轮,tag 已核:`#tree ul li` cv:auto + contain-intrinsic-size):离屏行只剩占位高度、**视口不扫过就永不布局**;深位置恢复从此依赖"占位估算准确+渐进渲染追上"。#65/#66(08-30 起)恰在上架两天后涌入——时间线吻合。
3. **v4.1.1 拆分拔掉掩蔽**(方向正确):高亮可关后,裸像素恢复路径暴露;R1 修复又(正确地)给 focus 加 preventScroll,拽动的三重兼职全部消失——死锁与补偿类问题自此完全裸露。**教训:移除一个有副作用的历史行为时,必须清点它无意中提供的全部服务**(拽动的"访问目标区"性质直到 R5 才以 walk 形式补回)。

## 3. 逐轮记录(根因 / 措施 / 验证 / 未竟原因)

### R1 — `9c705125`(随 v4.1.2,2026-09-02)

- **症状**(#65 Ownsin、#66 leungwh):高亮关后重开回顶;点击书签返回后位置漂移或回顶。
- **根因**(真弹窗实测):换树后嵌套 `#tree ul ul` 高度 ~250ms 才收敛,恢复赋值被静默 clamp;`focus()` 默认滚入视口(Chromium 程序化焦点滚动,overflow:hidden 杂技从未生效)。
- **措施**:赋值未达且每帧重试(上限 30 帧,期间 scrollTop 被外部移动即让位);三处 focus 加 `{preventScroll:true}`。
- **验证**:单元 +7;真浏览器 diag-issue65-66 A/B/C/D 场景修复后 5/5。
- **为何没修完**:①30 帧(≈500ms)预算对慢机大树不足——高亮 ON 时 focusID 使 chunk 门退让、强制同步整树解析,更慢;②**补写爬升中间值被滚动监听回写**,"爬升中关窗"即污染存储(用户"不能保存精确的位置"的直接机理);③restoreFocusSpot 放弃路径的裸 focus() 漏网。且**本地六维矩阵全部不可复现**(快机布局瞬时就绪),修复是实测+审计混合。→ #66 残余、#67(高亮开仍失败)、#68(高亮关深滚失败)。

### R2 — `44f3a517`(2026-09-04,随 4.1.3)

- **症状**:v4.1.2 上架后用户复验:高亮开仍不精确;维护者复现同。
- **根因**(代码审计,无可复现):R1 未竟①②③。
- **措施**:campaign 化(30 rAF + 40×100ms 尾段 ≈4.5s);**rescueApplied 握手**(监听跳过 campaign 自身值,真实滚动立即接管并持久化);focusDefault preventScroll。
- **验证**:rescue 组重写 +3 契约;diag 7/7、真弹窗矩阵、memory-layers 14/14。
- **为何没修完**:纯审计式(本地不可复现),按假设"布局终会收敛"延长预算——**不知道存在永不收敛的死锁**(cv 惰性布局),也不知道锚定补偿会与 campaign"决斗"。→ 维护者字面步骤仍必漂移。

### R3 — `1e4ef0a7`(2026-09-04,随 4.1.3)

- **症状**:维护者给出精确步骤(高亮开→点开非空文件夹→重开→滚深处→重开)必漂移。
- **根因**(隔离探针实证):**滚动锚定焦点劫持**——Chromium 锚定优先选聚焦元素为锚,视口外聚焦行使布局收敛期间的高度增长补偿把视口拽向焦点行(探针 scrollTop 400→0);preventScroll 挡不住(锚定是布局变更触发的独立机制)。
- **措施**:campaign 期间 body 置 `data-vbm-tree-settling`;reveal 焦点(.focus 闪烁仍即时)与 view-manager restoreFocusSpot 均待 campaign 落地后再 focus;锚定保留(误判为"net 正向",见未竟)。
- **验证**:+2 契约;diag 7/7、维护者字面步骤 2600 精确、memory-layers 14/14。
- **为何没修完**:①**"高亮关时锚点在视口内、补偿在保护视野"的判断只对了一半**——campaign 自身的"被外部滚动接管即让位"会把锚定补偿误判为用户滚动(决斗),且快走提前落地后锚定恢复时仍会拖拽(R6 实证 2600→7561);②本地 harness 布局仍瞬时就绪,六维矩阵照旧全绿——**不可复现环境下修复只能封已知路径**。→ 4.1.3 实测一轮。

### R4 — `498e0bc7`(分析轮,2026-09-04)

- **症状**(#68):高亮关、滚几页后必失效;半页正常——**深度不对称**是破案线索。
- **根因**(diag-68-slow-settle-duel 探针,userstyle 冻结样式确定性模拟慢收敛,首次本地复现):**cv 惰性布局死锁**——远离视口的子树样式变更不被重新布局(强制读 scrollHeight/offsetHeight 也不覆盖,上方下方皆然);savedTop 深于布局前沿即死锁:赋值 clamp 在前沿→视口到不了未布局区→永不布局→clamp 永不解。对抗序 PHASE A 卡 2199/2600,良性序 PHASE B 精确落地——半页/多页不对称即前沿位置。
- **历史复盘**(本轮双实证):问题类为 4.1.0 cv 亲手制造(v4.1.0 tag 核实);v4.1.0 裸 `focus()` 的拽动一直在掩蔽(兼任位置恢复+破死锁+回写自洽)。

- **症状**(维护者实测②):同操作,有时第一次重开确实记住且纹丝不动;之后每次继续开,落点各不相同。

## 4. 为什么修了这么多轮才收敛——结构性教训

1. **不可复现环境下的"全绿"是结构性盲区**:headless 无占位阶段(整树在赋值前布局完),R1–R3 三轮的真机条件在本地根本不存在;直到 R4(冻结样式模拟慢收敛)与 R6(行冻结模拟占位几何)建立了确定性模型,每一层根因才得以实证。**规则:凡"本地全绿+用户必现",第一优先级是造出差异的环境模型,而不是继续审计代码。**
2. **自己的性能优化制造了问题类**:cv:auto(4.1.0)是一切层级的共同上游;每轮修复都在与它的某个下游症状作战。引入 cv 时的假设"占位首估即准、滚动条首滚自愈"在深滚动恢复场景不成立。
3. **移除历史行为必须清点其隐性服务**:4.1.2 给 focus 加 preventScroll(正确)移除了裸拽动的三重兼职(近似恢复/破死锁/回写自洽),"访问目标区"性质直到 R5 walk 才补回。
4. **锚定的双重人格**:同一机制在稳态保护视野、在收敛期劫持视野,且其"内容稳定型补偿"会让像素静改——任何与锚定共存的恢复逻辑必须(a)在自身存续期压制它(R6),(b)以内容而非像素为不变式(R7)。
5. **不变式选错,修不完是必然**:R1–R6 全部围绕"像素精确"打转;跨会话几何互异+内容稳定补偿使该目标在语义上不可达。R7 换锚(行)后此类问题整体失效。

## 5. 现状与已知边界(截至 R7 / bba9127c)

- **已封**:回顶(clamp)、爬升污染、预算饿死、惰性死锁、焦点劫持、campaign 期决斗、give-up 迟到污染、跨会话像素游走。
- **已知边界(有意保留,非缺陷)**:①恢复后像素与保存值可能差若干像素——行/偏移不变式下属预期(补偿在守护内容);②行锚偏移可差 ±1-2px(换行行高的舍入);③`scrollAnchor` 指向的行被删除(书签变更)时回退纯像素路径;④view-manager 各列表视图的 viewState 仍是像素记忆——列表行高均匀且无 cv 之外的几何漂移源,风险面不同,未随本轮改造(如复现同类反馈再评估);⑤锚经 elementFromPoint 采样视口顶缘,与"视口中部"的行可能相差 1-2 行——记忆与恢复两侧采样一致,自洽。
- **待观察**:真机(维护者环境)对 R7 的复验结果;若仍有异动,下一诊断优先级=行锚本身的稳定性(打印 `scrollAnchor` 序列)。
